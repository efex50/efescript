# E7.4: mods written in Rust, C and C++ (wasm to efevm), design

Status: E7.4a (this document's guest side) and E7.4b (the translator, crate `efe-wasm`)
implemented 2026-11-20; E7.4c is designed here and not built. Related: `crates/efevm/API_INDEX.md` (the index and the engine
event ABI), `crates/efevm/SPEC.md` 9.1 to 9.3 (sections 12 to 14), `docs/e8-design.md`
(mod packages), `docs/e7-cranelift-design.md` (the JIT, unrelated but the same VM).

## 1. Summary and decisions

A mod may be written in Rust or C/C++, compiled to `wasm32-unknown-unknown` (or clang's
`wasm32`), and then run on efevm like any `.efa` mod. There is no wasm runtime in the engine:
a translator turns the `.wasm` into an `.efvm` module.

| Phase | What | Where | Status |
|---|---|---|---|
| E7.4a | The guest side: bindings generated from `.efapi` (Rust and C), the guest runtime crate/header, the ABI and custom-section formats (this document) | `crates/efescript/src/{bindmodel,rustgen,cgen}.rs`, `crates/efe-guest` | done |
| E7.4b | The translator: `.wasm` to `.efvm` (new crate `efe-wasm`, no unsafe, pure data) | `crates/efe-wasm` | done |
| E7.4c | Integration: `efescript pack` of a wasm mod, dev-time loading in the engine, cache | later | designed here |

**Decision (packaging).** `efescript pack` translates the wasm at pack time, so a `.efmod`
contains `module.efvm` and never wasm. The engine has no wasm parser on the package path.
In development, a mod folder may contain a built `.wasm`; the engine translates it on load
behind a cargo feature and caches the result in the existing `ScriptCache`, like `.efa`
(E7.4b/c). Consequences: the attack surface of untrusted packages stays the efevm decoder and
verifier; a translator bug can only produce a module the verifier then checks; web builds
(which ship `.efmod` files) need no translator.

## 3. The ABI

The ABI is what E7.4b must implement. It is defined by the `.efapi` signature and the rules
below; the generated bindings are one implementation of it.

### 3.1 Imports

For a host function `namespace.name` of an index whose namespace has version `v`:

- wasm import module: `"<namespace>@<v>"`, for example `"engine.world@2"`;
- wasm import name: the function name (`"get"`).

The module name carries the version the guest was generated against: the translator
records `(namespace, v)` in section 12 for every distinct import module, and the normal link
check (`namespace engine.world is version 3, module was built against version 2`) applies.
A function name never contains a dot, which keeps event imports (3.4) unambiguous.

### 3.2 Types

wasm32 has 32-bit pointers. Lowering from the `.efapi` type to wasm values:

| API type | wasm params | wasm result | efevm values (the translator widens) |
|---|---|---|---|
| `i32` | `i32` | `i32` | `i32` |
| `i64` | `i64` | `i64` | `i64` |
| `f32`, `f64` | `f32`, `f64` | same | same |
| `bool` | `i32` (0 or 1) | `i32` | `i32` |
| `entity` | `i64` | `i64` | `i64` |
| `ptr` | `i32` | `i32` | `i64` |
| `&Struct` | `i32` | not allowed | `i64` |
| `str`, `bytes` | `i32 ptr, i32 len` | not allowed | `i64 ptr, i64 len` |

Pointers, `&Struct` and both halves of `str`/`bytes` are `i32` on wasm; the translator
**zero-extends them to `i64` using the `.efapi` signature** (an import's wasm type and the
index signature are compared; the zero-extension is emitted at the call site, and a `ptr`
result is wrapped back with `i32.wrap_i64`, an address above 4 GiB cannot occur because linear
memory is at most 4 GiB). A signature that does not match the lowering of the index is a
translation error naming the function (`import game@1::log has (i32, i64), the index says
(str) = (i32, i32)`). At most one result; a function with several results in the index cannot be
used from Rust or C (the generators reject it).

efevm keeps `i32` values zero-extended in 64-bit registers (SPEC 2), so a wasm `i32` used as an
address needs no extra instruction before a load.

`Entity` is the 64-bit handle (`hecs::Entity::to_bits`). In Rust it is the `repr(transparent)`
newtype `efe_guest::Entity(u64)`; in C `typedef struct { uint64_t bits; } efe_entity;`. Both
are one `i64` by the wasm C ABI (a single-field aggregate is passed as the field), which the
Rust test checks on the built module.

### 3.3 Structs and memory

- Struct layouts are the `#[repr(C)]` layouts of the index: field offsets, size and alignment
  are exactly the index values (wasm32 `u64`/`f64` alignment is 8, as in efevm memory). The
  generators insert explicit padding fields where the index has gaps and assert `size_of`,
  `align_of` and every offset at compile time.
- **wasm address 0 is efevm address 0.** wasm memory 0 becomes efevm memory with the same
  contents and layout; the page size is 64 KiB in both. A pointer the guest passes to the host
  is an address in this memory; no translation happens.
- A struct pointer passed to a host function is read by the host (`&Struct` is shared). If the
  host writes through a `ptr` argument (as `engine.world.get(.., out)`), the index types it
  `ptr`, and the guest passes `*mut u8`.

### 3.4 Events

A guest names, sends and reads typed events through the existing `engine.events` ABI
(API_INDEX.md, "Engine ABI"), without a section of its own: **the section 14 list is derived
from the imports.**

For an event `E` of namespace `N` (version `v`), the guest imports from module `"<N>@<v>"`:

| wasm import name | wasm signature | efevm lowering |
|---|---|---|
| `E.send` | `(i32 payload)` with a payload, `()` without | `engine.events.send(ev, zext(payload))`, `0` for no payload |
| `E.count` | `() -> i32` | `engine.events.count(ev)` |
| `E.read` | `(i32 index, i32 out) -> i32` (events with a payload only) | `engine.events.read(ev, index, zext(out))`, status 0 or -1 |

The name contains a dot, so it cannot be a function (function names are identifiers). The
translator, for each distinct `(N, E)` it sees, in order of `(namespace, name)`:

1. looks `E` up in the index it is given (the `.efapi`, whose hash must equal `efe.api`), to get
   the payload struct and its size;
2. adds `(N, E, payload)` to section 14; the event id is its position in that list (so ids
   follow a deterministic order and never depend on the engine);
3. records `N` and its version in section 12;
4. emits the three lowered calls above with the id as a constant.

The module also gets the imports `engine.events.send`, `.count`, `.read` (and section 12 for
`engine.events`), as the `.efa` assembler does for `import event`. The namespace permissions
of section 14 apply as for any module (`ModuleData::event_namespaces()`). The generated helper
for an event is a module `game::score_changed` with `send(&Payload)`, `count()`, `read(i)` and
`iter()` (Rust), or `game_score_changed_send/_count/_read` (C).

Events a mod *provides* (declared in its own namespace) are section 13 events: see
`provide_event!` / `EFE_PROVIDE_EVENT` and the `efe.provide` record of kind 1 (4.3).

### 3.5 Provided functions (exports)

A function the mod provides to other mods or the game is a wasm export named
`efe_provide_<name>` (the `<name>` of the provide); its wasm signature is the lowering of its
record (3.2, applied to the record's parameter types, results are scalar). The translator
turns each record into a section 13 `provide` whose function index is that export's function.
Pointer arguments (`str`, `bytes`, `&Struct`) point into the **scratch region** the embedder
copied the data into (SPEC 9.2); the region is the wasm export `efe_scratch` (a global whose
value is its address) with the size of the `scratch` record. `ptr` cannot be provided.

## 4. Custom sections

All custom sections are optional for a module that is not a mod. A guest crate links exactly
one bindings file, so `efe.api` appears once; `efe.provide` is the concatenation of every
record in the crate (the linker concatenates custom sections of the same name).

### 4.1 `efe.api`

8 bytes: the index hash as `u64` little-endian (`ApiIndex::hash()`, FNV-1a 64), exactly the
hash field of section 12. (An earlier draft said 32 bytes; the index hash is 64-bit, so the
section is 8. If a stronger hash is ever wanted it belongs in the index format first.) The
namespaces of section 12 are not stored: they are the import module names (`ns@version`) of
3.1, so they cannot disagree with the imports. The translator is given the `.efapi` (merged
like `--api`) and rejects a module whose `efe.api` differs from the index hash, naming both;
that is the build-skew check.

### 4.2 `efe.provide`

A sequence of records, in link order:

```
record  = u8 kind, uleb32 body_len, body            (a reader skips kinds it does not know)
kind 0  = function: string name, string export, string doc,
                    params, results
kind 1  = event:    string name, u8 pflag [string payload struct], string doc
kind 2  = scratch:  uleb32 size                      (at most one; the region is export `efe_scratch`)
params  = uleb32 count, (string name, apitype)*
apitype = u8: 0 i32, 1 i64, 2 f32, 3 f64, 4 bool, 5 entity, 6 str, 7 bytes,
              8 struct (followed by string struct name)       -- the section 13 codes
string  = uleb32 length, UTF-8 bytes
```

- `export` is `efe_provide_<name>` (3.5); a record whose export is missing is a translation
  error. `results` is empty or one entry named `result`. `ptr` has no code (SPEC 9.2).
- Docs are the Rust `///` lines (or the C string) joined with `\n`, one leading space stripped
  per line; a doc must contain a non-blank character (the verifier requires it).
- The writers may use padded two-byte uleb values (the C header does); readers accept any
  valid LEB128 of at most 5 bytes.
- The record maps field for field to a section 13 `provide` / `pevent` and, for kind 2, to the
  `scratch` pair (offset from the `efe_scratch` global, size from the record). Structs named by
  `&Struct` parameters are copied from the index the translator is given, with the owner the
  index records (the same as the assembler's "copied structs"). Mod-defined structs would need
  a record of kind 3 (not defined yet: no example needs it).
- The translator also checks that each export's wasm signature equals the lowering of its record.

### 4.3 How the guest emits them

- **Rust.** `#[cfg_attr(target_arch = "wasm32", unsafe(link_section = "efe.api"))] #[used] static`
  in the generated file; `provide!`, `provide_event!` and `scratch!` of `efe-guest` build
  each record in a `const` and put it in a `#[used]` static in section `efe.provide`. Verified:
  the test builds the guest and parses the sections.
- **C/C++.** Checked with clang 21 and lld 22 (E7.4b): `__attribute__((section(".custom_section.X")))`
  on a variable does **not** make a wasm custom section; the bytes land in a data segment. Inline
  assembly does: `__asm__(".section .custom_section.efe.api,\"\",@\n.byte ...\n.section .text,\"\",@\n")`
  (the wasm assembler has no `.pushsection`). So:
  - `efe.api` (8 constant bytes) is emitted by the generated `efe_api.h` with that inline assembly
    under `#ifdef __wasm__`, in the one translation unit that defines `EFE_API_IMPLEMENTATION`.
    On a native target the header keeps the `static const uint8_t[8]` in an ELF section named
    `.custom_section.efe.api`, which the native test reads back with `objcopy`.
  - `efe.provide` is **not emitted for wasm**. `EFE_PROVIDE`, `EFE_PROVIDE_EVENT*` and
    `EFE_SCRATCH` still build the records (a native build keeps them in the ELF section, so the
    byte format stays tested) but for wasm they are unused statics. A C mod keeps the exports
    `efe_provide_<name>` (`EFE_EXPORT_AS`) and `efe_scratch`, and gives its provides to the
    translator through the fallback of 4.4. The records are valid C and not C++ (hence "EFE_PROVIDE
    needs C").
- **Linker.** No system `wasm-ld` is needed: rustup ships lld as `gcc-ld/wasm-ld`, and clang takes it
  with an absolute `-fuse-ld=<path>` (`--ld-path` is ignored by clang's wasm driver).

### 4.4 Fallbacks

If a toolchain cannot emit the sections (clang for wasm as measured in 4.3, Zig, a language without
section attributes), nothing else changes: the translator takes the **hash from the `.efapi` it is
given** (the build-skew check is then only as good as the build's discipline, unless the module has
`efe.api`) and the **provides from a fallback**: `efe_wasm::TranslateOptions::fallback`, a plain data
value (`Fallback { provides: Vec<FallbackProvide { name, export, doc, params, results }>, events,
scratch }`, the fields of the records of kind 0, 1 and 2 with `ApiType`s). The fallback is merged
with the section: a provide, event or scratch size named by both must be identical, else the
translation fails (`provide `x`: the fallback and the efe.provide record of the module disagree`).
The fallback comes from `mod.toml` at pack time (a `[[provide]]` table with name, export, doc, params
and results using the index spelling, e.g. `params = ["a: i32", "s: str", "c: &Score"]`, plus
`scratch = 4096`); parsing that table into a `Fallback` is part of E7.4c, `efe-wasm` has no toml
dependency. The C example test passes the fallback and checks section 13 in full.

## 5. Building a guest

- Rust: crate type `cdylib`, `#![no_std]`, `efe-guest` as a dependency (it provides the global
  allocator and the trapping `#[panic_handler]`; disable its default features to bring your own,
  and `std` mods cannot use the panic handler). `cargo build --release --target
  wasm32-unknown-unknown`. `panic = "abort"` is advisable.
- **Do not use browser-style flags.** The translator supports a plain single-threaded module:
  no atomics, no shared memory, and the memory is defined by the module, not imported. A
  developer's cargo config for web builds (`-C target-feature=+atomics`, `--shared-memory`,
  `--import-memory`, as the engine's own web build uses) makes the module import `env.memory`
  and the translator rejects it with a message that names these flags. The guest test sets
  `RUSTFLAGS` to override such a config.
- C: `clang --target=wasm32 -nostdlib -O2 -Wl,--no-entry -Wl,--export=efe_scratch mod.c`.
  `efe_scratch` is exported with `--export` (a data symbol); functions are exported by
  `EFE_PROVIDE` through `export_name`.

## 6. The bindings generator

`efescript api-export --rust <file.efapi|.efmod>... [-o api.rs]` and
`efescript api-export --c <...>... [-o efe_api.h]`. Several inputs are merged with
`ApiIndex::merge` (the game's index plus the mods it depends on, as `--api` does). Output is a
pure function of the merged index: sorted, no dates. Header: `@generated`, the game name and the
hash. The generator is `bindmodel` (language-neutral: namespace tree, struct layouts with
explicit padding, wasm lowering, single-result rule) plus a thin spelling backend each.

Rust file (a module of the guest crate, `mod api;`; it starts with inner attributes):

- Namespaces are **nested modules**, one per dotted segment: `engine.world` is `engine::world`
  (`engine` is also a module of its own). Each has `NAMESPACE` and `VERSION` constants.
- `pub mod raw` in each namespace holds the `unsafe extern "C"` imports with
  `#[link(wasm_import_module = "<ns>@<v>")]` and `#[link_name = "<function>"]`, with wasm-level
  types (`i32` for bool, `*const u8, usize` for str/bytes, `*const Struct`, `*mut u8` for ptr).
- Safe wrappers (same names, doc comments from the index plus the index signature) take
  `&str`, `&[u8]`, `&Struct`, `bool`, `Entity`; they are `unsafe fn` when a parameter is a
  raw `ptr`.
- Structs sit at the top level: `#[repr(C)]` (with `align(N)` when the index asks for more than
  the fields), `Clone, Copy, Debug, PartialEq`, `SIZE`, `COMPONENT` (engine components),
  `zeroed()`, `Default`, `GuestStruct::NAME`, and `const` asserts of size, alignment and every
  field offset.
- Each event is a module inside its namespace (`game::score_changed`).
- Names: Rust keywords are escaped (`r#match`, `r#type`); `self`, `crate`, `super`, `Self`
  and `_` cannot be raw identifiers and are an error; so are structs named like a primitive
  or `Entity`, a namespace or event that collides with a struct or the `raw` module, a function
  with several results, parameters that collide after lowering, an invalid index, and
  mod-defined `mod:` components used as a payload. Every error names the item in index
  spelling; no broken code is ever emitted.

C header: include guard `EFE_API_H`, `typedef struct { uint64_t bits; } efe_entity;`, one
`efe_<Name>` struct per layout with `EFE_STATIC_ASSERT` (`_Static_assert` or C++
`static_assert`) on size, alignment and offsets, and `EFE_COMPONENT_<Name>`; every function is
a declaration with `__attribute__((import_module("<ns>@<v>"), import_name("<name>")))` named
`<namespace with dots as underscores>_<name>`; `str` and `bytes` are `(const char* / const
uint8_t*, size_t)` pairs named `<param>_ptr`, `<param>_len`; events are
`<ns>_<event>_send/_count/_read`; docs are `/** */` comments; `<NS>_VERSION` macros. C and C++
keywords used as parameter or field names get a trailing `_`. Name collisions of the flattened
C names (`g.a_b` against `g.a` + `b`) are an error.

## 7. E7.4b: the translator

New crate `efe-wasm` (name open), pure data like `efevm::api`: `translate(wasm: &[u8], index:
&ApiIndex, options) -> Result<efevm::Module, TranslateError>`, with `wasmparser` (the
translator's only dependency on the wasm side; the engine's package path never links it).

**Supported subset.** MVP (all numeric, control, memory, call, call_indirect, locals, globals,
select, `br_table`), sign-extension ops, non-trapping float-to-int (efevm `trunc_sat`),
mutable globals (efevm globals), **bulk memory** `memory.copy` and `memory.fill` (efevm has
both; LLVM emits them for `memcpy` and `memset` by default on current rustc), multi-value
(blocks with parameters, functions with several results; efevm calls have several results).
Rejected with a clear error naming the construct: atomics and shared memory, SIMD, exceptions,
GC types, tail calls, memory64, multi-memory, extended-const, relaxed SIMD,
`memory.init`/`data.drop` and passive segments, reference types beyond one `funcref` table 0
(`table.get/set/grow/fill`, `ref.*`), imported memory/table/globals, more than one memory,
floating-point features outside IEEE (none).

**Mapping.**

- Code: structured control flow to efevm basic blocks and labels; a register allocator that
  gives each wasm local one register and each stack slot a temp (a first version may map the
  operand stack height to fixed registers: wasm validation guarantees the height at every point).
  `i32` values stay zero-extended (SPEC 2), so no extra instructions for addresses.
- **Memory:** wasm memory 0 is efevm memory (address 0 = address 0, 64 KiB pages, same min and
  max); active data segments with an `i32.const` offset become section 8; a load/store is
  `reg[base] (u64) + offset` in both, with the same out-of-bounds trap.
- Globals: wasm globals become efevm globals (`__stack_pointer` is just a mutable `i32`).
- **Function table:** wasm table 0 and its active element segments become section 4
  (`function index + 1`, `0` = unset: wasm's null index 0 reserved by LLD maps to unset
  exactly); `call_indirect type` maps to efevm's with the same type check (`Trap::UndefinedElement`
  for out of range or unset, `Trap::IndirectCallTypeMismatch`).
- **Start function:** efevm has no start section. If the module has a start function or exports
  `__wasm_call_ctors`, the translator adds a mutable `i32` global `initialized` and prepends to
  every provided function (and every export) `if !initialized { initialized = 1; call start }`.
  (A flag, not a constructor run at load: the engine instantiates modules without calling into
  them; the first call of the mod does the work, once per instance.)
- **Traps:** `unreachable` is efevm `unreachable` (`Trap::Unreachable`). A Rust panic (the
  `efe-guest` handler) and a C `__builtin_trap()` compile to `unreachable`, so they trap with a
  location (the wasm function name from the `name` section is copied to section 10 and, if DWARF
  is present, lines to section 11 later). The other wasm traps map one to one:
  out of bounds, divide by zero, integer overflow (`INT_MIN / -1`), invalid conversion,
  indirect-call errors, stack exhaustion (efevm `max_call_depth`). Out-of-fuel is the efevm
  budget, which wasm lacks. Rust's shadow stack lives at the bottom of memory (wasm-ld's default
  `--stack-first` layout), so an overflow of it traps with an out-of-bounds access, not silent
  corruption.
- Imports: 3.1 to 3.4; the `engine.events` functions for events; unknown imports and wrong
  signatures are errors. `memory.grow` maps to efevm `memory.grow` (same result convention:
  old size in pages or -1; efevm returns `i64`, the translator wraps).
- Output sections: 12 from `efe.api` (hash) plus the import namespaces; 13 from `efe.provide`;
  14 from the event imports (3.4); `names` from the wasm `name` section. The module is then
  verified by `Module::verify` like any other.

**Tests.**

1. The translator's own unit tests per instruction against expected efevm output.
2. **Differential fuzzing against a real wasm runtime**, with `wasmi` (or `wasmtime`) as a
   dev-dependency only: a seeded generator (as `efevm-jit`'s) writes random valid wasm modules
   within the subset, runs the exported functions in the runtime and in efevm (interpreter and
   JIT) with the same arguments and memory, and compares results, traps (kind), final memory and
   globals. The wasm module bytes come from `wasm-encoder`-style building in the test crate. A
   second, lighter loop translates the corpus of real guests (the examples here, and the
   `efe-guest` fixtures) and runs them against a host mock that implements the imports.
3. Every import and export of the example guests round-trips: provide records to section 13
   to `Interface::index` equal to the index the generator saw.

## 8. E7.4c: packing and loading

- `efescript pack DIR`: if `mod.toml` names a `[build] wasm = "path.wasm"` (or `entry` ends in
  `.wasm`), pack translates it with the merged `--api` inputs and writes `module.efvm` into
  the package as for an `.efa` entry; manifest checks (id, provides against section 13,
  permissions against the imports and section 14) are unchanged. `inspect` shows it as usual;
  no wasm ever enters a package.
- `efescript api-export --rust|--c` on a `.efmod` (a dependency) is already supported: the
  mod's own index becomes bindings, which is how one wasm mod calls another mod's provides.
- Engine, development only: a folder mod whose `mod.toml` points at a `.wasm` is translated on
  load by the engine behind the cargo feature `wasm-mods` (off by default, native only), with
  the result cached in `ScriptCache` keyed by the wasm bytes, the index hash and the translator
  version, and invalidated when the wasm file changes (same hot-reload path as `.efa`). Release
  builds leave the feature off and load `.efmod` only.
- The debugger shows wasm function names; source lines come later from DWARF.

## 9. Decisions on the open questions of E7.4b

All of these are implemented in `crates/efe-wasm` (see its `structure.md`).

1. **Crate.** `efe-wasm` in `crates/`, mirrored into the efescript repo by
   `scripts/sync_efescript.py` (listed in `CRATES` and `MEMBERS`). API:
   `translate(wasm, &ApiIndex, &TranslateOptions) -> Result<efevm::Module, TranslateError>` (the
   result is verified) and `TRANSLATOR_VERSION` for cache keys. Errors name the construct, the wasm
   function (index and name) and the byte offset.
2. **Register limit.** A function that needs more than efevm's 65535 registers (locals plus the
   operand stack, one register per stack slot) is rejected with a size error (`TooLarge`); there is no
   splitting.
3. **`ptr` and widening.** Done as in section 3.2: an `i32` register is zero-extended, so arguments
   need no instruction; a `ptr` result gets `i32.wrap_i64`. A provided function with `str`, `bytes` or
   `&Struct` parameters gets a small wrapper function with the efevm (`i64`) signature that wraps the
   pointers and calls the wasm function (section 13 requires the lowered type exactly). No provided
   function needs a 64-bit address (`ptr` cannot be provided).
4. **Mod-defined structs and own-namespace imports.** Out of scope for now: unknown `efe.provide`
   record kinds (including the not yet defined kind 3) are skipped, and an import whose namespace is
   not in the index (also the mod's own) is an `UnknownNamespace` error naming it. Imports of
   namespaces that are in the index but not part of the `engine.events` ABI are normal functions.
5. **Constructors.** The lazy flag, not a load hook: a mutable `i32` global `initialized` is added
   when the module has a start function or exports `__wasm_call_ctors`, and every exported function
   (including an exported or provided import, which gets a wrapper) starts with
   `if flag == 0 { flag = 1; call start; call ctors; flag = 2 }` (start first). The start function and
   `__wasm_call_ctors` themselves, when exported, run once: called first they run the initialisation
   (which includes them) and return; called later they return at once. A trap in the start function
   does not run it again.
6. **Passive segments.** `memory.init`, `data.drop` and passive (and declarative) segments are
   rejected. Not observed in Rust release builds of the example guest (wasm-ld emits active segments
   without `--shared-memory`).
7. **Zig and clang.** Still untested for Zig (no Zig installed). clang 21 with lld 22 was run: the
   C guest translates and runs. `__attribute__((section(".custom_section.X")))` does not produce
   custom sections there (the bytes land in data segments); inline assembly does. Decision: `efe.api`
   is emitted by `efe_api.h` with file-scope inline assembly under `__wasm__`; `efe.provide` is not
   emitted for C wasm, the provides come from the translator's fallback (4.4, implemented as
   `TranslateOptions::fallback`; the `mod.toml` parsing stays in E7.4c). See 4.3 for the linker.
8. **Debug info.** The wasm `name` section function names are copied to section 10 (export names
   fill the gaps); DWARF is ignored. Each wasm function keeps its efevm instructions in order, so
   lines can be mapped later.

Also decided while building: a missing `efe.api` section is accepted (the given index's hash is used,
4.4; `TranslateOptions::require_efe_api` insists on it); `engine.events` is recorded in section 12
only when the index has that namespace (the guest fixture's index has not, and its imports and
events still link, because the translator knows the three signatures); a host function that is
used through the function table or exported gets a wrapper function with the wasm signature.

Hardening after a review: only core modules are accepted (components are an error) and every module
part and operator is checked against an allow-list, with the validator limited to the features the
subset uses; GC `rec` groups, subtypes, shared types and exact function types, `v128` or reference
types in block types and `select` are rejected; an active data segment (also an empty one) must fit
the initial memory; a memory without a maximum gets the wasm32 maximum of 65536 pages; `efe_scratch`
must be an immutable `i32` global.
